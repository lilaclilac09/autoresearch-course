Experiment Loop and Scaling Out: From Zero to Running

Your job is no longer to run experiments. Your job is to write good experiment instructions — and then go to sleep.

Quickstart: five steps from zero to your first experiment

🚀
Deploy an unattended research team

Think of autoresearch as a research team you've hired. You are the PI (principal investigator), and program.md is the research protocol you've written for the team. Once everything's set up, you go home — the team works through the night and reports results in the morning.

1
Install uv
uv is a Python package manager 10–100x faster than pip. Install it first, then sync deps: 
curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync
Only needs to be done once.
2
Prepare data
Download the climbmix dataset shards and train the BPE tokenizer — about 2 minutes, only once: 
uv run prepare.py
When it finishes you'll have local data shards and a tokenizer.
3
Run training manually once
Run one full training pass to verify the environment works. After about 5 minutes you'll see val_bpb output: 
uv run train.py
That number is your baseline; every subsequent improvement is measured against it.
4
Start the AI agent
Open Claude or Codex CLI inside this repo and send the launch prompt: 
"Take a look at program.md, start a new experiment! Do the setup first."
The agent reads program.md, checks git state, then starts its first experiment loop.
5
Go to sleep
The AI agent runs the loop autonomously, all night. In the morning, check results.tsv — you'll find a complete experiment log of keeps, discards, and crashes. Each experiment is ~5 minutes, so 8 hours ≈ 96 experiments.

🔴
What if it crashes?

If uv run train.py crashes (e.g. OOM), the agent runs tail -n 50 run.log to read the error, then records status=crash in results.tsv, runs git reset back to the last good state, and tries a more conservative idea.

How do you write a good program.md?

📝
program.md is the most important thing you produce as a research PI

It's not just instructions — it's how you program the AI's research ability. The better it's written, the more direction the AI agent has, and the less budget it wastes on low-value attempts.

program.md: bad vs good ❌ Bad program.md: "Try various improvements, find the best val_bpb" ✓ Good program.md: "Priority exploration: 1. Optimizer hyperparams (LR, betas, warmdown) 2. Architecture variants (GQA ratio) 3. Attention pattern (SSSL vs SSL) If 3 discards in a row, try a directional reset."
Why write it this way?
The bad version: too vague. The AI will wander randomly, burning experiment budget on low-value attempts — like telling a new hire "go make this project work".
The good version: gives priorities and a structured search space — like a senior researcher telling a new hire "start here, then explore in this order".
Encode domain knowledge: e.g. "Muon is sensitive to learning rate, sweep within 0.02–0.06 first" — this is where you add real value as a human.
Simplicity principle: Karpathy deliberately added "simpler code is better", to stop the AI from introducing overly complex tricks just to chase val_bpb.
NEVER STOP rule: ensures the agent keeps iterating through the night, even when the search space gets hard, and doesn't wait for human guidance.
🔄
program.md is itself iterative

You observe the AI's research behavior, notice it taking detours — always tuning the same parameter, for example — then add constraints or new directions to program.md. The next restart, it's smarter. This is the codification of human research skill.

Running on smaller hardware + the bigger picture

💻
Running autoresearch on a MacBook / small GPU

The official version targets H100 (80GB VRAM). But community forks for macOS / AMD / Windows exist. On non-H100 machines, the key adjustments are:

  • DEPTH: drop from 8 to 4 — a shallower model massively reduces memory
  • TOTAL_BATCH_SIZE: drop from 219 to 214 (~16K), reduces per-step gradient accumulation overhead
  • WINDOW_PATTERN: change to 'L' (drop short-window SSSL), more efficient on MPS / CPU
  • Swap the dataset: consider using TinyStories instead of climbmix — much smaller, so small models can still produce sensible results
  • Community forks: for macOS see miolini/autoresearch-macos; for AMD see andyluo7/autoresearch

The bigger picture

autoresearch is just three files, one GPU, and one overnight run — but it points to a fundamental shift in how AI-assisted research works.

👤
The human's role is shifting

From "manual hyperparameter tuner" → "author of research instructions". The core skills become: reading results, forming hypotheses, encoding domain knowledge into program.md. In Karpathy's own words: "The era of meat computers doing frontier AI research is long gone."

🔬
The limits of AI-driven research

autoresearch only optimizes a single metric ( val_bpb ). Real research breakthroughs still require humans to ask the right questions and design the right evaluation criteria — those parts AI can't replace yet.

♻️
A reusable framework

This three-file architecture transplants to any domain: quant-trading strategy iteration, drug molecule optimization, program synthesis. Fixed evaluator + mutable target + human-authored instructions = a universal pattern.
