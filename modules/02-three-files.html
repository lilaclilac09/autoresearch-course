Three-File Architecture

Boundaries are the design — this repo has only three key files. But the way the boundaries between them are drawn determines how the entire system works.

Three files, three roles

Think of this system as a standardized scientific experiment: the lab equipment must stay uniform (no privately fiddling with the instrument's dial); the experimental variables are the things you actually want to tune; the experimental plan is the research protocol the researcher writes before any experiment begins.

🔒
prepare.py

Fixed infrastructure — data download, BPE tokenizer training, data loader, the evaluate_bpb evaluation function. The AI agent cannot modify anything in here. "Fixed" is the whole point — it guarantees that experiments are comparable, and it's the foundation of the system's integrity.

⚗️
train.py

The experiment target — GPT model architecture, MuonAdamW optimizer, training loop. This is the only file the AI agent edits. All hyperparameters and architectural choices are fair experimental variables. Every experiment starts here: the AI agent makes changes, runs them, records the result.

📋
program.md

Research-organization code — humans define experiment goals, boundaries, and loop rules here. This is the human's leverage: iterate on program.md to improve the AI's research ability. It's not code, it's an "instruction set" — telling the AI agent the rules of this research game.

prepare.py — why is it off-limits?

Fixing the evaluate_bpb evaluation logic is the foundation of the system's integrity — if the AI could modify the eval function, it could easily "cheat" by making the numbers look better without actually improving the model.

prepare.py # Fixed constants — do not modify MAX_SEQ_LEN = 2048 # context length TIME_BUDGET = 300 # training time budget (seconds) EVAL_TOKENS = 40 * 524288 # validation tokens VOCAB_SIZE = 8192 # BPE vocab size # Dataset: climbmix-400b-shuffle BASE_URL = "https://huggingface.co/..." VAL_SHARD = 6542 # fixed validation shard def evaluate_bpb(model, dataloader): # ← AI agent can never touch this ...
Line-by-line
MAX_SEQ_LEN = 2048
Max token length per training sample; sets how much context the model can "see".
TIME_BUDGET = 300
Fixed 5-minute time budget. Every experiment runs for the same amount of time, so results are comparable.
EVAL_TOKENS = 40 × 524288
Validation set fixed at about 21M tokens, so every evaluation is consistent and not skewed by differing sample counts.
VAL_SHARD = 6542
Always uses the same validation shard, eliminating "data leakage": training and validation sets are strictly separate.
evaluate_bpb function
This is the "ground truth". The AI can't change it — and that's what guarantees the integrity of the whole system.
🔏
Why is this rule so critical?

If the AI agent could modify how val_bpb is computed, it could make any bad model look "better". Pinning the eval function down means experiment results are real, not hallucinated through "optimization".

train.py — hyperparameters hard-coded right into the source

No CLI flags, no YAML config files. Hyperparameters are just Python variables, and the AI agent edits the code directly — simple, direct, easy to diff.

train.py # Model architecture DEPTH = 8 # number of Transformer layers ASPECT_RATIO = 64 # model_dim = depth × this HEAD_DIM = 128 # attention head dim WINDOW_PATTERN = "SSSL" # attention window pattern # Optimization TOTAL_BATCH_SIZE = 2**19 # ~524K tokens/step EMBEDDING_LR = 0.6 # embedding LR MATRIX_LR = 0.04 # matrix-param LR (Muon) WEIGHT_DECAY = 0.2 WARMDOWN_RATIO = 0.5 # LR warmdown duration ratio # Hardware DEVICE_BATCH_SIZE = 128
Line-by-line
DEPTH=8 + ASPECT_RATIO=64
→ The Transformer hidden dim is model_dim = 8 × 64 = 512. Change to DEPTH=12 and model_dim becomes 768 — a big jump in capacity.
WINDOW_PATTERN = "SSSL"
Most layers (S) use short-window attention to save compute; the last layer (L) is forced to use the full context to capture long-range dependencies.
TOTAL_BATCH_SIZE = 219
About 524K tokens per step. If the batch size exceeds GPU memory, gradient accumulation splits it automatically inside train.py — no manual tweaking needed.
EMBEDDING_LR=0.6 / MATRIX_LR=0.04
Two LRs: embeddings use AdamW (LR=0.6), matrix weights use the Muon optimizer (LR=0.04).
WARMDOWN_RATIO = 0.5
Warmdown takes 50% of total training time. The LR linearly decays to 0 in the second half — standard modern LLM training practice.
💡
Why no CLI flags or config file?

Keeping hyperparameters live in the code means every `git diff` clearly shows "what changed in this experiment". The design choice itself reflects a simplicity principle — one less abstraction layer, one less place for things to go wrong.

The simplicity principle

program.md states it explicitly: "All else equal, simpler is better. A +0.001 val_bpb improvement that adds 20 lines of ugly code? Probably not worth it. Deleting code and getting the same effect? Absolutely keep."
