The Big Picture: AI as Researcher

What autoresearch does, why it works, and how Karpathy implemented an autonomous research loop with a minimal design.

You wake up. The AI has run 100 experiments overnight.

🌙
Opening scene

10 PM, you launch an AI agent. 8 AM, you wake up. It has completed 100 experiments, and the model's language-modeling loss is 3% lower than the night before. Nobody stayed up. Nobody hand-tuned parameters. This is autoresearch.

autoresearch is an experimental project Karpathy released in March 2026. The core idea is extremely simple: hand a real LLM training pipeline over to an AI agent and let it iterate by itself — modify the training code, run experiments, look at results, decide to keep or discard — round and round, all night.

Why is "fixed 5 minutes" a genius design choice?

⏱️
Time budget, not step budget

Whether you make the model bigger or smaller, double the batch size or halve it, every experiment runs for exactly 5 minutes. This makes experiments across different architectures directly comparable, with no need to manually align training step counts. Big models train slower per step, but within 5 minutes they still compete on the same starting line as small ones.

After every experiment, autoresearch emits a structured metrics report. The key number is val_bpb (validation bits per byte), which is independent of BPE vocabulary size and can be compared directly across architectures.

Example output --- val_bpb: 0.997900 training_seconds: 300.1 total_seconds: 325.9 peak_vram_mb: 45060.2 mfu_percent: 39.80 total_tokens_M: 499.6 num_steps: 953 num_params_M: 50.3 depth: 8
Line-by-line
val_bpb: validation bits per byte, lower is better, unaffected by vocabulary size
training_seconds: actual training time, fixed at ~300s (5 minutes)
total_seconds: total time including data loading and overhead
peak_vram_mb: peak GPU memory usage in MB
mfu_percent: model FLOPs utilization, measures how efficiently the GPU's compute is actually used
total_tokens_M: total tokens consumed by this training run (in millions)
num_params_M: model parameter count (in millions)
depth: Transformer layer count — deeper means more expressive power, but slower
💡
How are results recorded?

Every experiment appends a row to results.tsv, with columns: commit (git commit hash), val_bpb, memory_gb, status (keep / discard / crash), description (the AI agent's description of the change). By morning you have a full experiment log.

02

Three-File Architecture

Boundaries are the design — this repo has only three key files. But the way the boundaries between them are drawn determines how the entire system works.

Three files, three roles

Think of this system as a standardized scientific experiment: the lab equipment must stay uniform (no privately fiddling with the instrument's dial); the experimental variables are the things you actually want to tune; the experimental plan is the research protocol the researcher writes before any experiment begins.

🔒
prepare.py

Fixed infrastructure — data download, BPE tokenizer training, data loader, the evaluate_bpb evaluation function. The AI agent cannot modify anything in here. "Fixed" is the whole point — it guarantees that experiments are comparable, and it's the foundation of the system's integrity.

⚗️
train.py

The experiment target — GPT model architecture, MuonAdamW optimizer, training loop. This is the only file the AI agent edits. All hyperparameters and architectural choices are fair experimental variables. Every experiment starts here: the AI agent makes changes, runs them, records the result.

📋
program.md

Research-organization code — humans define experiment goals, boundaries, and loop rules here. This is the human's leverage: iterate on program.md to improve the AI's research ability. It's not code, it's an "instruction set" — telling the AI agent the rules of this research game.

prepare.py — why is it off-limits?

Fixing the evaluate_bpb evaluation logic is the foundation of the system's integrity — if the AI could modify the eval function, it could easily "cheat" by making the numbers look better without actually improving the model.

prepare.py # Fixed constants — do not modify MAX_SEQ_LEN = 2048 # context length TIME_BUDGET = 300 # training time budget (seconds) EVAL_TOKENS = 40 * 524288 # validation tokens VOCAB_SIZE = 8192 # BPE vocab size # Dataset: climbmix-400b-shuffle BASE_URL = "https://huggingface.co/..." VAL_SHARD = 6542 # fixed validation shard def evaluate_bpb(model, dataloader): # ← AI agent can never touch this ...
Line-by-line
MAX_SEQ_LEN = 2048
Max token length per training sample; sets how much context the model can "see".
TIME_BUDGET = 300
Fixed 5-minute time budget. Every experiment runs for the same amount of time, so results are comparable.
EVAL_TOKENS = 40 × 524288
Validation set fixed at about 21M tokens, so every evaluation is consistent and not skewed by differing sample counts.
VAL_SHARD = 6542
Always uses the same validation shard, eliminating "data leakage": training and validation sets are strictly separate.
evaluate_bpb function
This is the "ground truth". The AI can't change it — and that's what guarantees the integrity of the whole system.
🔏
Why is this rule so critical?

If the AI agent could modify how val_bpb is computed, it could make any bad model look "better". Pinning the eval function down means experiment results are real, not hallucinated through "optimization".

train.py — hyperparameters hard-coded right into the source

No CLI flags, no YAML config files. Hyperparameters are just Python variables, and the AI agent edits the code directly — simple, direct, easy to diff.

train.py # Model architecture DEPTH = 8 # number of Transformer layers ASPECT_RATIO = 64 # model_dim = depth × this HEAD_DIM = 128 # attention head dim WINDOW_PATTERN = "SSSL" # attention window pattern # Optimization TOTAL_BATCH_SIZE = 2**19 # ~524K tokens/step EMBEDDING_LR = 0.6 # embedding LR MATRIX_LR = 0.04 # matrix-param LR (Muon) WEIGHT_DECAY = 0.2 WARMDOWN_RATIO = 0.5 # LR warmdown duration ratio # Hardware DEVICE_BATCH_SIZE = 128
Line-by-line
DEPTH=8 + ASPECT_RATIO=64
→ The Transformer hidden dim is model_dim = 8 × 64 = 512. Change to DEPTH=12 and model_dim becomes 768 — a big jump in capacity.
WINDOW_PATTERN = "SSSL"
Most layers (S) use short-window attention to save compute; the last layer (L) is forced to use the full context to capture long-range dependencies.
TOTAL_BATCH_SIZE = 219
About 524K tokens per step. If the batch size exceeds GPU memory, gradient accumulation splits it automatically inside train.py — no manual tweaking needed.
EMBEDDING_LR=0.6 / MATRIX_LR=0.04
Two LRs: embeddings use AdamW (LR=0.6), matrix weights use the Muon optimizer (LR=0.04).
WARMDOWN_RATIO = 0.5
Warmdown takes 50% of total training time. The LR linearly decays to 0 in the second half — standard modern LLM training practice.
💡
Why no CLI flags or config file?

Keeping hyperparameters live in the code means every `git diff` clearly shows "what changed in this experiment". The design choice itself reflects a simplicity principle — one less abstraction layer, one less place for things to go wrong.

03

Anatomy of a Modern GPT

What's actually packed into train.py? — Cracking open a race-car engine: every part has a reason to be there, every improvement is backed by a paper.

Eight modern improvements at a glance

The GPT in train.py is not 2019's GPT-2. It's a careful mix of 8 improvements that Karpathy hand-picked from 2024–2025 frontier research. Each improvement is an independent experimental knob — turn off Value Embedding, switch the SSSL pattern, change the softcap value, all are fair game.

⚡
RMSNorm

Replaces LayerNorm — simpler and faster, no mean computation needed. The standard choice for modern LLMs; used in LLaMA and Mistral.

🔄
RoPE

Rotary positional embeddings — encodes position by rotating Q/K vectors instead of adding to them. Extrapolates to lengths unseen during training.

🗂️
GQA

Grouped query attention — fewer K/V heads than Q heads, shrinks KV cache, enables larger batch sizes in training.

🔀
Value Embedding

A ResFormer improvement: injects token embedding info into the V vector, enabled on alternating layers, with a gate controlling the mix ratio. Improves gradient flow.

🪟
Sliding-window attention

SSSL pattern: most layers only see the first half of the sequence (efficient), the last layer is forced to see the full sequence — balances efficiency and global view.

📐
Squared ReLU

MLP activation uses relu² — sparser than GELU (more exact zeros), faster to compute, and empirically just as good or better.

🧢
Softcap logits

From Gemma 2: tanh-based soft truncation of logits, preventing numerical blowup that destabilizes training. Smoother than a hard clip.

🧭
Muon optimizer

Gradient-orthogonalizing optimizer — uses Newton-Schulz iteration to make every update step "maximally distinct", avoiding repeated movement in the same direction.

🔬
The AI agent's experimental space

Each of these 8 improvements maps to a hyperparameter or toggle. The AI agent can systematically enable/disable each improvement and measure its impact on MFU and validation loss, automatically producing ablation reports.

Attention trio: GQA + Value Embedding + RoPE

Three improvements work together to form the attention core in train.py. On the left is the simplified actual code; on the right, a line-by-line explanation.

Python # QKV projection (GQA: K/V heads can be fewer) q = self.c_q(x).view(B, T, n_head, head_dim) k = self.c_k(x).view(B, T, n_kv_head, head_dim) v = self.c_v(x).view(B, T, n_kv_head, head_dim) # Value Embedding (only on alternating layers) if ve is not None: gate = 2 * torch.sigmoid( self.ve_gate(x[..., :32])) v = v + gate.unsqueeze(-1) * ve # RoPE rotary positional embedding q = apply_rotary_emb(q, cos, sin) k = apply_rotary_emb(k, cos, sin) # QK norm (prevents attention-weight blowup) q, k = norm(q), norm(k) # Flash Attention 3 (hardware acceleration) y = fa3.flash_attn_func( q, k, v, causal=True, window_size=window_size)
Line-by-line
q / k / v shape difference
q has shape (B, T, n_head, head_dim); k/v have shape (B, T, n_kv_head, head_dim). The clever bit of GQA: when n_kv_head < n_head, multiple Q heads share one K/V group, cutting down both KV cache and compute.
ve_gate: input-driven mix gate
Computes a gate value from the first 32 dimensions of input x (sigmoid output 0–1, multiplied by 2 to give range 0–2), controlling how much Value Embedding to mix into the current v vector. Since the gate depends on the input, the model adaptively decides how much "raw embedding info" each token needs.
apply_rotary_emb: position via rotation
Pairs up dimensions of q/k and rotates each pair by an angle that depends on the token's position. When two positions are at a fixed relative distance, their dot product naturally reflects that relative distance — no extra positional embedding table needed, and it generalizes to longer sequences than seen during training.
window_size: SSSL sliding window
In the SSSL pattern, S layers only see the first half of the sequence (window_size = T/2), L layers see all of it (window_size = T). Flash Attention 3 handles the sliding window directly in the kernel — no Python-level masking required.
🔄
RoPE intuition: rotation = relative position

Say token A is at position 3 and token B is at position 7 — relative distance is 4. RoPE rotates qA by 3θ and kB by 7θ; their dot product contains (7−3)θ = 4θ, which depends only on relative position. Traditional learned positional embeddings can't do this, and positions never seen during training can still be rotated — that's why RoPE "extrapolates".

MLP + advanced stability tricks: Squared ReLU, Softcap, ResFormer residuals

Beyond the attention layer, train.py modernizes the MLP activation, output normalization, and residual connections. These three changes each look small, but together they make training more stable and help gradients flow deeper.

Python # MLP: Squared ReLU class MLP(nn.Module): def forward(self, x): x = self.c_fc(x) x = F.relu(x).square() # relu² x = self.c_proj(x) return x # Softcap (from Gemma 2) softcap = 15 logits = softcap * \ torch.tanh(logits / softcap) # ResFormer residual mix x = self.resid_lambdas[i] * x + \ self.x0_lambdas[i] * x0
Line-by-line
relu² (Squared ReLU)
Sparser than GELU — many activations are exactly 0 (only positive values are kept, and they're squared). Faster to compute. Experimentally, it's as good or better than GELU, with no GELU approximation error.
softcap: softly pins logits to [−15, 15]
In raw backpropagation, unbounded logit growth saturates softmax and kills gradients. softcap softly caps with tanh rather than hard-clipping — derivatives exist everywhere, gradient flow stays intact, and training stability improves significantly.
resid_lambdas: residual scaling
Each layer independently learns a scaling factor, initialized to 1.0 (equivalent to standard residual connections). During training the model can adapt the residual strength per layer.
x0_lambdas: original-embedding injection
x0 is the layer-0 input (raw token embedding). Every layer mixes in a small amount of x0 (initially 0.1), ensuring deep layers can still access the original semantic info — improving deep gradient flow.

MuonAdamW optimizer: make gradients orthogonal

🧭
Muon: orthogonalize the gradient

Standard SGD/Adam use the gradient directly to update weights. Muon first projects the gradient matrix onto orthogonal directions — using Polar Express Newton-Schulz iteration to compute the orthogonalized matrix — then updates. This makes every update "maximally distinct" from previous ones, avoiding repeated motion in the same direction, equivalent to a steepest-descent step in weight-update space.

Python param_groups = [ # AdamW handles embeddings and scalars dict(kind='adamw', params=embedding_params, lr=EMBEDDING_LR * dmodel_lr_scale, betas=ADAM_BETAS), # Muon handles matrix params dict(kind='muon', params=matrix_params, lr=MATRIX_LR, momentum=0.95, ns_steps=5), # N-S iteration count ]
Line-by-line
AdamW handles "non-matrix" params
token embeddings (wte), lm_head, resid_lambdas, x0_lambdas — these are vectors or scalars, can't be matrix-orthogonalized, so they keep using AdamW.
Muon handles all 2D matrices
Attention layers' c_q / c_k / c_v / c_proj, and the MLP's c_fc / c_proj — all 2D weight matrices. After orthogonalization, every update direction is "maximally distinct" from prior steps.
dmodel_lr_scale = (dim / 768)−0.5
Following μP (maximal update parametrization) theory, as model dim grows, the LR should shrink. This scaling factor lets models of different sizes train in the same reasonable LR range.
ns_steps=5: Newton-Schulz precision
5 Polar Express iterations are enough to give a sufficiently accurate orthogonalization. Each iteration computes a matrix polynomial; convergence is superlinear (5 steps brings error to negligible).
1
Adam: momentum + adaptive LR

Maintains first/second moment estimates of the gradient and adjusts per-parameter step size. Direction is decided by the raw gradient — may oscillate across correlated dimensions.

2
Muon: orthogonal gradient → update

First compute an orthogonalized version G_orth of the gradient matrix G (Newton-Schulz iteration), then apply momentum on G_orth. Every step walks "a new path" through weight space.

3
Use both, each for its job

Matrix params use Muon (benefit from orthogonal directions); non-matrix params use AdamW (not orthogonalizable, traditional route). Hence the name MuonAdamW.

04

Experiment Loop and Scaling Out: From Zero to Running

Your job is no longer to run experiments. Your job is to write good experiment instructions — and then go to sleep.

Quickstart: five steps from zero to your first experiment

🚀
Deploy an unattended research team

Think of autoresearch as a research team you've hired. You are the PI (principal investigator), and program.md is the research protocol you've written for the team. Once everything's set up, you go home — the team works through the night and reports results in the morning.

1
Install uv
uv is a Python package manager 10–100x faster than pip. Install it first, then sync deps: 
curl -LsSf https://astral.sh/uv/install.sh | sh
uv sync
Only needs to be done once.
2
Prepare data
Download the climbmix dataset shards and train the BPE tokenizer — about 2 minutes, only once: 
uv run prepare.py
When it finishes you'll have local data shards and a tokenizer.
3
Run training manually once
Run one full training pass to verify the environment works. After about 5 minutes you'll see val_bpb output: 
uv run train.py
That number is your baseline; every subsequent improvement is measured against it.
4
Start the AI agent
Open Claude or Codex CLI inside this repo and send the launch prompt: 
"Take a look at program.md, start a new experiment! Do the setup first."
The agent reads program.md, checks git state, then starts its first experiment loop.
5
Go to sleep
The AI agent runs the loop autonomously, all night. In the morning, check results.tsv — you'll find a complete experiment log of keeps, discards, and crashes. Each experiment is ~5 minutes, so 8 hours ≈ 96 experiments.

What if it crashes?

If uv run train.py crashes (e.g. OOM), the agent runs tail -n 50 run.log to read the error, then records status=crash in results.tsv, runs git reset back to the last good state, and tries a more conservative idea.

How do you write a good program.md?

📝
program.md is the most important thing you produce as a research PI

It's not just instructions — it's how you program the AI's research ability. The better it's written, the more direction the AI agent has, and the less budget it wastes on low-value attempts.

program.md: bad vs good ❌ Bad program.md: "Try various improvements, find the best val_bpb" ✓ Good program.md: "Priority exploration: 1. Optimizer hyperparams (LR, betas, warmdown) 2. Architecture variants (GQA ratio) 3. Attention pattern (SSSL vs SSL) If 3 discards in a row, try a directional reset."
Why write it this way?
The bad version: too vague. The AI will wander randomly, burning experiment budget on low-value attempts — like telling a new hire "go make this project work".
The good version: gives priorities and a structured search space — like a senior researcher telling a new hire "start here, then explore in this order".
Encode domain knowledge: e.g. "Muon is sensitive to learning rate, sweep within 0.02–0.06 first" — this is where you add real value as a human.
Simplicity principle: Karpathy deliberately added "simpler code is better", to stop the AI from introducing overly complex tricks just to chase val_bpb.
NEVER STOP rule: ensures the agent keeps iterating through the night, even when the search space gets hard, and doesn't wait for human guidance.
🔄
program.md is itself iterative

You observe the AI's research behavior, notice it taking detours — always tuning the same parameter, for example — then add constraints or new directions to program.md. The next restart, it's smarter. This is the codification of human research skill.

Running on smaller hardware + the bigger picture

💻
Running autoresearch on a MacBook / small GPU

The official version targets H100 (80GB VRAM). But community forks for macOS / AMD / Windows exist. On non-H100 machines, the key adjustments are:

  • DEPTH: drop from 8 to 4 — a shallower model massively reduces memory
  • TOTAL_BATCH_SIZE: drop from 219 to 214 (~16K), reduces per-step gradient accumulation overhead
  • WINDOW_PATTERN: change to 'L' (drop short-window SSSL), more efficient on MPS / CPU
  • Swap the dataset: consider using TinyStories instead of climbmix — much smaller, so small models can still produce sensible results
  • Community forks: for macOS see miolini/autoresearch-macos; for AMD see andyluo7/autoresearch

The bigger picture

autoresearch is just three files, one GPU, and one overnight run — but it points to a fundamental shift in how AI-assisted research works.

👤
The human's role is shifting

From "manual hyperparameter tuner" → "author of research instructions". The core skills become: reading results, forming hypotheses, encoding domain knowledge into program.md. In Karpathy's own words: "The era of meat computers doing frontier AI research is long gone."

🔬
The limits of AI-driven research

autoresearch only optimizes a single metric ( val_bpb ). Real research breakthroughs still require humans to ask the right questions and design the right evaluation criteria — those parts AI can't replace yet.

♻️
A reusable framework

This three-file architecture transplants to any domain: quant-trading strategy iteration, drug molecule optimization, program synthesis. Fixed evaluator + mutable target + human-authored instructions = a universal pattern.
